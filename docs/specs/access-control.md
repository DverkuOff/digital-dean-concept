# Спека: вход, сессии и контроль доступа

Статус: реализовано 17.11.2026. Тесты: `e2e/01-security.spec.ts`.

## Модель угроз (из брифа §5)
1. Студент открывает чужую заявку или профиль, подставив id в адрес (IDOR).
2. Студент вызывает действие методиста (смена статуса) напрямую, минуя интерфейс.
3. Подмена id в скрытом поле формы.
4. Утечка пароля из БД.
5. Секреты в коде или в браузере.
6. Перебор паролей.

## Вход
- Better Auth, плагин `username`: вход по логину и паролю. Регистрации нет (`disableSignUp: true`), аккаунты создаёт деканат (в демо — сид).
- Хеш пароля: **argon2id** (`@node-rs/argon2`, m=19 MiB, t=2, p=1 — рекомендация OWASP), `src/server/password.ts`. В БД `account.password` начинается с `$argon2id$v=19$m=19456,t=2,p=1$`.
- Сессия: случайный токен в cookie `httpOnly`, `SameSite=Lax`, `Secure` при https; запись сессии в БД, срок 7 дней.
- Роль (`student` | `staff`) — поле `user.role`, `input: false`: передать её с клиента нельзя.
- Rate limit Better Auth: `/sign-in/username` — 10 попыток в минуту с адреса.

## Где проверяется доступ

| Слой | Что делает | Защита? |
|---|---|---|
| `src/proxy.ts` | Без cookie сессии — редирект на `/login` | **Нет**, только удобство (cookie может быть поддельной; CVE-2025-29927 показал, что middleware можно обойти) |
| `src/server/session.ts` | `requireStudent()` / `requireStaff()`: настоящая сессия из БД + роль | Да |
| `src/server/dal/*` | Каждый запрос к данным студента содержит `WHERE student_id = <id из сессии>` | Да, главный рубеж |
| `src/server/actions/*` | Server Actions = публичные POST-эндпоинты: сессия, роль и владелец проверяются внутри каждого action; `student_id` никогда не берётся из формы | Да |

### Правила для кода (их же проверяет ревью ИИ-кода)
1. Страница и action не импортируют `db` напрямую ради данных студента — только через DAL.
2. Владелец — **в условии выборки**, а не проверкой после неё: `and(eq(request.id, id), eq(request.studentId, me.id))`.
3. Не нашли — `notFound()` (404). Чужая запись неотличима от несуществующей, существование не раскрываем.
4. Невалидный id (не UUID) отсекается до запроса к БД (`isUuid`) → 404, а не 500.
5. Студенческий раздел: проверка в `(student)/layout.tsx`, кабинет методиста — в `staff/layout.tsx`; студент на `/staff` получает 404.
6. Методист меняет статус только по таблице переходов `STAFF_TRANSITIONS` (`src/lib/requests/catalog.ts`); причина обязательна для «вернуть» и «отклонить».
7. Агрегаты по однокурсникам (место на курсе) отдаются только числами, без имён и id.

## Подписка на календарь (без сессии)
`GET /api/calendar/<токен>.ics` открывают календарные приложения, а они не шлют cookie. Поэтому пропуск — сам токен:
- 32 случайных байта (base64url), не id студента и не производное от него;
- в БД только SHA-256 токена (`calendar_token.token_hash`), сам токен показывается студенту один раз;
- перевыпуск заменяет хеш — старая ссылка сразу даёт 404;
- строгий формат (43 символа) проверяется до запроса к БД; неизвестный токен → 404;
- в ответе только пары группы владельца токена; `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`.
Тест: `e2e/07-calendar.spec.ts`.

## Заметки к парам
`lesson_note` (студент, пара, текст). Чтение — `LEFT JOIN` с условием `student_id = свой` прямо в соединении, поэтому чужие заметки в выборку не попадают. Запись (`saveLessonNoteAction`): пара проверяется условием `lesson.group_code = группа из сессии`, автор берётся из сессии. Тест `e2e/10-notes.spec.ts`: Орлов подменяет `lessonId` на пару группы Соколовой → «Пара не найдена», в БД заметка Соколовой не изменилась. Проверен на поломку: без условия на группу тест падает.

## Поиск
`searchAction` (Server Action) берёт студента из сессии. Заявки и оценки выбираются с `WHERE student_id = свой`, новости — общие и своего факультета, разделы и каталог — статические списки. Запрос ограничен 60 символами, спецсимволы LIKE экранируются. Тест `e2e/09-search.spec.ts`: номер чужой заявки и фамилия однокурсника ничего не находят.

## Почему 404, а не 403
403 подтверждает, что запись существует. 404 одинаков для «нет такой» и «не ваша».

Тонкость Next.js: если страница стримится (есть `loading.tsx` над ней), `notFound()` после начала стрима отдаёт статус 200. Поэтому у `/requests/[id]` нет `loading.tsx` выше по дереву: скелетон списка заявок лежит в группе `requests/(list)`, а проверка роли — в layout, который рендерится до стрима.

## Секреты
- `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` — только переменные окружения; имена в `.env.example`, значений в репозитории нет.
- Нет переменных с префиксом `NEXT_PUBLIC_`, ключей ИИ в прототипе нет (LLM не используется).
- Заголовки: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`.

## Персональные данные
Все данные вымышлены (сид). Медицинские документы не загружаются — в заявке «уважительная причина» есть пометка, что это персональные данные особой категории (152-ФЗ, ст. 10).
